# NapitkiBerkat Spec Workflow

## Главное правило

Считать проектные документы источником правды.

Работать в таком порядке:

```text
spec -> plan -> code
```

Нельзя реализовывать поведение, которого нет в specs. Если требование неясно или противоречит документации, нужно остановиться и уточнить до разработки.

## Начало любой задачи

Из корня проекта:

1. Прочитать `AGENTS.md`, если он еще не прочитан в текущей задаче.
2. Прочитать `docs/00-global-spec.md`, чтобы понять общий смысл проекта.
3. Прочитать только нужные документы глубже:
   - `docs/features/` - если задача про поведение функции;
   - `docs/technical/` - если задача про техническую реализацию;
   - `docs/user-stories/` - если задача про путь пользователя;
   - `docs/01-development-roadmap.md` - если задача про порядок разработки.
   - `docs/work-plans/` - если задача про конкретный план разработки.
   - `docs/roadmap/` - если задача про историю выполненных работ.
4. Использовать `rg`, чтобы найти связанные требования перед правкой документации или кода.

Не загружать все docs в контекст без необходимости. Читать только те файлы, которые нужны для текущей задачи.

## Определить слой задачи

Перед действием понять, к какому слою относится запрос пользователя:

- **Global spec** - цель проекта, роли, общий scope, границы первой версии.
- **Feature spec** - подробное поведение конкретной части продукта.
- **Technical spec** - база данных, API, архитектура, хранение, авторизация, деплой.
- **User stories** - реальные пользовательские сценарии и проверки.
- **Roadmap / work plan** - порядок разработки и проверяемые этапы.
- **Code** - только после того, как нужные specs и план понятны.

Если во время разработки появляется новая идея или новая функция, сначала обновить или подтвердить соответствующий spec.

## Работа с документацией

Когда нужно править docs:

1. Найти правильный слой документации.
2. Не дублировать детали между слоями без необходимости.
3. Держать global spec общим.
4. Держать feature specs про поведение.
5. Держать technical specs про реализацию.
6. Держать user stories как проверку пользовательских путей, а не место для новых требований.
7. Не удалять принятые решения без явного подтверждения владельца.

Когда пользователь просит проверить docs, сначала перечислить:

- прямые противоречия;
- серые зоны;
- недостающие решения;
- лишние повторы;
- устаревшие формулировки.

Сначала перечислить находки. Редактировать только после подтверждения владельца, если пользователь не попросил сразу исправить.

## Работа с разработкой

Перед написанием кода:

1. Найти feature/technical specs, которые разрешают эту работу.
2. Проверить, что задача соответствует roadmap или текущему work plan.
3. Составить маленький план реализации с проверяемыми шагами и сохранить его в `docs/work-plans/active/`.
4. После утверждения work plan работать по Git/GitHub-правилам из `AGENTS.md`: отдельная ветка, разработка, проверки, commit, push, Pull Request.
5. Реализовать только согласованный scope.
6. Проверить результат тестами, командами, локальным запуском или понятной ручной проверкой.
7. Когда владелец протестировал результат и попросил сделать push на GitHub, перенести work plan из `docs/work-plans/active/` в `docs/work-plans/completed/`.
8. Обновить дорожную карту: `docs/roadmap/timeline.md` и нужные файлы в `docs/roadmap/areas/`.
9. Кратко описать, что изменено и что проверено.

Если specs и код расходятся, specs главнее, пока владелец не подтвердит изменение документации.

## Правила проекта

- Каталог, админка, кнопки, ошибки, пустые состояния и все пользовательские тексты должны быть на русском языке.
- Сообщения commit должны быть на русском языке.
- Не добавлять регистрацию, личный кабинет, онлайн-оплату, CRM, точные складские остатки, автоматический расчет доставки, автоматическую проверку города или сложные роли админки, пока это не появится в specs.
- Не хранить секреты в репозитории.
- Git/GitHub workflow брать из `AGENTS.md`.
- Не удалять старые импортные или исходные данные без явного подтверждения владельца.

## Когда нужно остановиться

Остановиться и уточнить, если:

- требования нет в specs;
- specs противоречат друг другу;
- решение влияет на бизнес-поведение;
- можно потерять данные;
- задача касается секретов, деплоя, production-данных Supabase или оплаты.

Вопросы задавать коротко и конкретно.
