# AGENTS.md

## Назначение

Этот файл описывает правила работы AI-агентов в проекте **Каталог NapitkiBerkat**.

Главное правило проекта:

```text
Сначала spec -> потом plan -> потом code
```

Если требования нет в документации, его нельзя делать в коде. Если требование неясно, его нужно уточнить. Если требование противоречит уже утвержденным specs, работу нужно остановить до уточнения.

## Язык работы

- Общение с владельцем проекта ведется на русском языке.
- Документация проекта пишется на русском языке.
- Сам проект, клиентский каталог, админка, все пользовательские тексты, кнопки, сообщения, ошибки и состояния интерфейса пишутся на русском языке.
- Сообщения commit пишутся на русском языке, чтобы владелец понимал историю изменений.
- Технические названия файлов, папок, API, переменных и команд можно писать на английском.

## Структура документации

Основные документы проекта находятся в `docs/`.

Текущие слои документации:

- `docs/00-global-spec.md` - общее понимание проекта;
- `docs/features/` - подробные feature specs;
- `docs/technical/` - technical specs;
- `docs/user-stories/` - user stories.
- `docs/work-plans/` - активные и завершенные планы разработки;
- `docs/roadmap/` - хронологическая дорожная карта выполненных работ;
- `.agents/skills/napitkiberkat-spec-workflow/` - project skill с правилами работы по specs.

Следующие слои могут быть добавлены позже:

- implementation notes.

## Правила изменения документации

- Не удалять принятые решения без явного подтверждения владельца.
- Не добавлять новую функциональность только потому, что она кажется полезной.
- Если появилась новая идея, сначала внести ее в подходящий spec.
- Если documents противоречат друг другу, сначала перечислить противоречия и дождаться подтверждения правок.
- Не смешивать разные слои документации без необходимости.
- Global spec должен оставаться общим и не дублировать все детали feature specs.
- Feature specs описывают поведение функций.
- Technical specs описывают техническую реализацию уже согласованного поведения.
- User stories проверяют реальные пути пользователей и не должны добавлять новую логику сами по себе.

## Правила разработки

Разработка кода запрещена, пока владелец явно не подтвердит переход к work plans и implementation.

До этого можно:

- читать документацию;
- создавать и править specs;
- искать противоречия и серые зоны;
- предлагать структуру документов;
- готовить черновики планов только после запроса владельца.

Нельзя:

- создавать приложение;
- писать компоненты;
- подключать Supabase;
- создавать базу данных;
- настраивать Vercel;
- писать production-код;
- устанавливать зависимости;
- делать миграции.

## Работа с work plans

Роудмап, work plans и дорожная карта не заменяют друг друга:

- `docs/01-development-roadmap.md` - общий маршрут первой версии;
- `docs/work-plans/` - конкретные планы отдельных веток;
- `docs/roadmap/` - история уже выполненных работ.

Когда владелец просит составить plan, AI-агент создает файл в `docs/work-plans/active/`.

Один work plan соответствует одной рабочей ветке Git.

Когда владелец после тестирования просит сделать push на GitHub:

1. Перенести plan из `docs/work-plans/active/` в `docs/work-plans/completed/`.
2. Обновить `docs/roadmap/timeline.md`.
3. Обновить нужные файлы в `docs/roadmap/areas/`.

Детали процесса описаны в `docs/work-plans/README.md` и `docs/roadmap/README.md`.

Этот раздел является быстрым ориентиром для AI-агентов.

Главный источник правды находится в `docs/`. Если эта выжимка расходится со specs, нужно опираться на `docs/` и сначала уточнить противоречие у владельца.

- Проект: **Каталог NapitkiBerkat**.
- Формат: каталог-сайт для оптового магазина напитков.
- Основной сценарий клиента: открыть ссылку, выбрать напитки, собрать заказ, отправить в WhatsApp.
- Клиентский каталог и админка полностью на русском языке.
- Заказы в первой версии отправляются в WhatsApp и не сохраняются в базе.
- Админка нужна владельцу для управления каталогом без разработки.
- База данных: Supabase Postgres.
- Фото: Supabase Storage.
- Размещение сайта: Vercel.

## Краткие ограничения первой версии

Это не полный список требований, а напоминание о границах первой версии.

В первой версии не делаем:

- регистрацию и личный кабинет клиентов;
- онлайн-оплату на сайте;
- разные цены для разных клиентов;
- точные складские остатки и CRM;
- автоматический расчет точной стоимости доставки;
- автоматическую проверку города в адресе;
- сложные роли в админке.

## Работа с Git и GitHub

Работа по разработке всегда идет через отдельную ветку, commit, push и Pull Request.

Для каждого утвержденного work plan:

1. Перед разработкой перейти на `main`.
2. Обновить `main` через `git pull --ff-only origin main`.
3. Создать отдельную ветку под этот план от актуальной `main`.
4. Делать изменения только в ветке этого плана.
5. После завершения разработки выполнить проверки, которые подходят этому плану.
6. Проверить `git status` и `git diff --check`.
7. Когда владелец после тестирования попросил сделать push на GitHub, перенести файл плана из `docs/work-plans/active/` в `docs/work-plans/completed/`.
8. Обновить `docs/roadmap/timeline.md` и нужные файлы в `docs/roadmap/areas/`.
9. Сделать commit с понятным сообщением на русском языке.
10. Сделать push ветки на GitHub.
11. Создать Pull Request в `main`.
12. Если после создания Pull Request появилась ссылка или номер PR, можно обновить запись дорожной карты дополнительным commit и push в ту же ветку. Если это неудобно или рискованно, оставить поле PR пустым.
13. После создания Pull Request вернуться на локальную ветку `main`.

Подтверждение work plan владельцем считается разрешением только на создание рабочей ветки и разработку по этому плану.

Commit, push и Pull Request можно делать только после того, как владелец протестировал результат и отдельно попросил сделать push на GitHub.

Владелец сам делает merge Pull Request на GitHub.

После того как Pull Request создан, нельзя начинать новый plan из старой рабочей ветки.

Когда владелец после merge просит продолжить работу:

1. Перейти на `main`.
2. Обновить `main` через `git pull --ff-only origin main`.
3. Только после этого создавать новый plan и новую ветку.

Если во время создания ветки, commit, push или Pull Request есть незавершенные чужие изменения, конфликт, отсутствует доступ к GitHub или команда небезопасна, нужно остановиться и уточнить у владельца.

Для обычных правок документации вне утвержденного work plan commit, push и Pull Request не делать без явной просьбы владельца.

Не откатывать чужие изменения без явной просьбы владельца.

Не использовать destructive-команды вроде `git reset --hard` без прямого указания владельца.

Не делать force push без прямого указания владельца.

## Безопасность

- Не хранить в репозитории пароли, ключи Supabase, ключи Vercel и другие секреты.
- Не коммитить `.env` с реальными значениями.
- `SUPABASE_SERVICE_ROLE_KEY` нельзя отправлять в браузер и нельзя хранить в клиентском коде.
- Админские действия должны проходить через проверку входа.

## Перед началом любой работы

AI-агент должен:

1. Сначала использовать project skill `napitkiberkat-spec-workflow` из `.agents/skills/napitkiberkat-spec-workflow/` как рабочий порядок для задач по документации, планам и разработке.
2. Понять, к какому слою относится задача: spec, user stories, technical spec, work plan или code.
3. Проверить существующие документы.
4. Убедиться, что задача не противоречит утвержденным решениям.
5. Если задача неясна, сначала уточнить.
6. Если задача ясна и относится к документации, внести точечные правки.
