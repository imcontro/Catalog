# AGENTS.md

## Назначение

Этот файл описывает правила работы AI-агентов в проекте **Каталог NapitkiBerkat**.

Главное правило проекта:

```text
Сначала spec -> потом plan -> потом code
```

Если требования нет в документации, его нельзя делать в коде. Если требование неясно, его нужно уточнить. Если требование противоречит уже утвержденным specs, работу нужно остановить до уточнения.

## Язык работы

- Общение с владельцем проекта ведется на русском языке.
- Документация проекта пишется на русском языке.
- Сам проект, клиентский каталог, админка, все пользовательские тексты, кнопки, сообщения, ошибки и состояния интерфейса пишутся на русском языке.
- Сообщения commit пишутся на русском языке, чтобы владелец понимал историю изменений.
- Технические названия файлов, папок, API, переменных и команд можно писать на английском.

## Правила изменения документации

- Не удалять принятые решения без явного подтверждения владельца.
- Не добавлять новую функциональность только потому, что она кажется полезной.
- Если владелец предложил новую идею, сначала внести ее в подходящий spec.
- Если документы противоречат друг другу, сначала перечислить противоречия и дождаться решения владельца.
- Не смешивать и не дублировать требования между слоями документации без необходимости.
- User stories не должны самостоятельно добавлять новые требования.

## Работа с work plans

Технические изменения можно выполнять только по утвержденному work plan и только в пределах задач, которые входят в этот plan.

В проекте не используется отдельный roadmap разработки.

Следующий план разработки определяется логически после завершения предыдущего плана: по актуальным specs, состоянию проекта и решению владельца.

Work plans и дорожная карта не заменяют друг друга:

- `docs/work-plans/` - конкретные планы отдельных веток;
- `docs/roadmap/` - история уже выполненных работ.

Когда владелец просит составить plan, AI-агент создает файл в `docs/work-plans/active/`.

Один work plan соответствует одной рабочей ветке Git.

Детали процесса описаны в `docs/work-plans/README.md` и `docs/roadmap/README.md`.

## Работа с Git и GitHub

Работа по разработке всегда идет через отдельную ветку, commit и push рабочей ветки.

Pull Request и merge владелец проекта делает сам на GitHub.

Для каждого утвержденного work plan:

1. Перед разработкой перейти на `main`.
2. Обновить `main` через `git pull --ff-only origin main`.
3. Создать отдельную ветку под этот план от актуальной `main`.
4. Делать изменения только в ветке этого плана.
5. После завершения разработки выполнить проверки, которые подходят этому плану.
6. Проверить `git status` и `git diff --check`.
7. Когда владелец после тестирования попросил сделать push на GitHub, перенести файл плана из `docs/work-plans/active/` в `docs/work-plans/completed/`.
8. Обновить `docs/roadmap/timeline.md` и нужные файлы в `docs/roadmap/areas/`.
9. Сделать commit с понятным сообщением на русском языке.
10. Сделать push ветки на GitHub.
11. Pull Request в `main` владелец создает сам на GitHub.
12. Merge Pull Request владелец делает сам на GitHub.
13. После сообщения владельца, что Pull Request создан и merge выполнен, перейти на локальную ветку `main`.
14. Обновить локальную ветку `main` через `git pull --ff-only origin main`.
15. Только после обновления локального `main` можно создавать новый plan и новую рабочую ветку.

Подтверждение work plan владельцем считается разрешением только на создание рабочей ветки и разработку по этому плану.

Commit и push можно делать только после того, как владелец протестировал результат и отдельно попросил сделать push на GitHub.

Pull Request и merge AI-агент не делает: владелец сам создает Pull Request и сам выполняет merge на GitHub.

После того как Pull Request создан, нельзя начинать новый plan из старой рабочей ветки.

Когда владелец сообщил, что Pull Request создан и merge выполнен на GitHub:

1. Перейти на `main`.
2. Обновить `main` через `git pull --ff-only origin main`.
3. Только после этого создавать новый plan и новую ветку.

Если во время создания ветки, commit, push или обновления локального `main` есть незавершенные чужие изменения, конфликт, отсутствует доступ к GitHub или команда небезопасна, нужно остановиться и уточнить у владельца.

Для обычных правок документации вне утвержденного work plan commit и push не делать без явной просьбы владельца.

Не откатывать чужие изменения без явной просьбы владельца.

Не использовать destructive-команды вроде `git reset --hard` без прямого указания владельца.

Не делать force push без прямого указания владельца.

## Перед изменением документации или кода

Этот порядок применяется к задачам, которые могут изменить требования, документацию, work plan или код. Для простых ответов на вопросы и проверок состояния Git читать specs не требуется.

AI-агент должен:

1. Понять ожидаемый результат задачи. Если он неясен, уточнить его у владельца.
2. Определить тип задачи и относящийся к ней слой: global spec, feature spec, design spec, technical spec, user stories, work plan, roadmap или code.
3. Самостоятельно выбрать и прочитать только относящиеся к задаче документы. Владелец не обязан указывать их названия или пути.
4. Если после анализа задачи нельзя однозначно выбрать документы, использовать skill `napitkiberkat-spec-workflow`.
5. Сверить задачу с прочитанными документами и убедиться, что она не противоречит утвержденным решениям.
6. При противоречии остановиться, перечислить его и дождаться решения владельца.
