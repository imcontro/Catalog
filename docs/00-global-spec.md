# Global Spec v0.4

## 1. Назначение документа

Этот документ является главным spec проекта **Каталог NapitkiBerkat**.

Он фиксирует общее понимание проекта:

- для кого создается проект;
- какую проблему он решает;
- какие роли есть в проекте;
- какой основной сценарий должен пройти клиент;
- какие крупные части входят в первую версию;
- какие главные правила нельзя нарушать при дальнейшем проектировании.

Детальное поведение отдельных частей описывается в feature specs. Дизайн и визуальные правила описываются в design specs. Техническая реализация, база данных, API, фреймворки и конкретная верстка описываются в technical specs и skills.

Проект ведется по правилу: сначала spec, потом plan, потом code. Если требования нет в spec, оно не делается. Если требование неясно, оно уточняется. Если требование противоречит spec, работа останавливается до уточнения.

## 2. Название проекта

Название проекта: **Каталог NapitkiBerkat**.

## 3. Суть проекта

Проект представляет собой каталог-сайт для оптового магазина напитков NapitkiBerkat.

Клиент получает ссылку на сайт, открывает ассортимент, смотрит цены, выбирает нужные товары и отправляет заказ в WhatsApp.

Главная идея: заменить ручную отправку ассортимента, цен и уточнений одним удобным каталогом, который помогает клиенту быстро понять ассортимент, цену, доступность товара, доставку и способ оформления заказа.

## 4. Для кого проект

Основные клиенты:

- кафе;
- рестораны;
- клиенты, которые заказывают напитки на дом;
- другие покупатели напитков.

Домашние клиенты идут по тому же сценарию, что кафе, рестораны и другие клиенты: открывают каталог, выбирают товары и отправляют заказ в WhatsApp.

Проект ориентирован не на случайный розничный просмотр, а на клиентов, которые уже заинтересовались покупкой и хотят быстро увидеть доступный ассортимент.

## 5. Основная проблема

Сейчас клиент часто спрашивает ассортимент и цены отдельно.

Показывать весь ассортимент вручную сложно, долго и неудобно:

- нужно каждый раз объяснять, какие товары доступны, а каких сейчас нет;
- нужно отправлять цены;
- нужно отвечать на повторяющиеся вопросы;
- клиенту сложно сравнивать товары;
- заказ может теряться в переписке;
- менеджер тратит много времени на однотипную коммуникацию.

## 6. Цели проекта

Клиентская цель:

- быстро увидеть ассортимент напитков;
- понять цены;
- найти товар по названию;
- выбрать нужные товары;
- сформировать заказ;
- увидеть сумму товаров, подсказку по бесплатной доставке и информацию по доставке;
- отправить заказ в WhatsApp.

Бизнес-цель:

- быстрее закрывать интерес клиента;
- уменьшить ручной труд при показе ассортимента;
- упростить процесс заказа;
- упростить понимание доставки;
- повысить вероятность, что клиент дойдет до заказа;
- дать владельцу удобный способ менять товары, цены, фото, вкусы, категории, сортировку в **Все напитки**, сортировку внутри категории и статус товара без разработки.

## 7. Роли проекта

### 7.1. Клиент

Клиент открывает каталог по ссылке, смотрит ассортимент, выбирает товары, указывает данные заказа и отправляет заказ в WhatsApp.

### 7.2. Владелец каталога

Владелец управляет каталогом через админку.

Он должен иметь возможность без разработки менять товары, цены, фото, вкусы, список категорий, категорию товара, сортировку в **Все напитки**, сортировку внутри категории, статус товара и удалять товары.

### 7.3. Работник магазина

Работник получает заказ в WhatsApp и должен быстро понять:

- какие товары заказали;
- какие вкусы выбраны;
- сколько упаковок нужно;
- какая сумма товаров;
- какая информация по доставке;
- куда доставлять;
- как клиент хочет оплатить заказ.

## 8. Основной сценарий клиента

1. Клиент пишет или звонит и интересуется ассортиментом.
2. Ему отправляют ссылку на каталог.
3. Клиент открывает каталог на телефоне или компьютере.
4. Клиент видит раздел "Все напитки" и может фильтровать товары по категориям.
5. Клиент выбирает товары в каталоге.
6. Клиент собирает заказ в корзине.
7. Клиент видит сумму товаров и подсказку по бесплатной доставке.
8. Клиент открывает оформление заказа.
9. Клиент указывает адрес доставки.
10. Клиент видит итоговую информацию по доставке.
11. Клиент выбирает способ оплаты.
12. Клиент нажимает "Отправить в WhatsApp".
13. В WhatsApp формируется понятное сообщение с заказом.
14. Работник магазина получает заказ и обрабатывает его в чате.

Основной канал передачи ссылки: WhatsApp или другая переписка с клиентом.

Приоритет устройства: **мобильный телефон**.

Сайт также должен нормально работать на компьютере.

## 9. Карта feature specs

Детальные правила первой версии описаны в отдельных feature specs:

- `01-client-catalog.feature-spec.md` - клиентский каталог, категории, карточки товаров, вкусы, поиск и видимость товаров;
- `02-cart.feature-spec.md` - корзина, количество упаковок, суммы, недоступные позиции и удаление товаров;
- `03-checkout-and-whatsapp.feature-spec.md` - оформление заказа, обязательные данные и WhatsApp-сообщение;
- `04-delivery.feature-spec.md` - правила отображения доставки;
- `05-admin-auth.feature-spec.md` - вход в админку;
- `06-admin-products.feature-spec.md` - управление товарами, категориями, вкусами, статусами, фото, ценами и сортировкой;
- `07-empty-and-error-states.feature-spec.md` - пустые, ошибочные и нестандартные состояния.

Global spec не должен дублировать все детали этих документов. Если нужна точная логика отдельной части, нужно смотреть соответствующий feature spec.

## 10. Что не входит в первую версию

В первую версию не входят:

- регистрация клиентов;
- личный кабинет клиента;
- разные цены для разных клиентов;
- минимальный заказ;
- акции и скидки;
- избранные товары;
- онлайн-оплата на сайте;
- автоматическая синхронизация со складом;
- точные остатки товара в штуках;
- сложная CRM;
- сложная система ролей и прав доступа;
- полноценный интернет-магазин с оплатой на сайте.

Эти возможности можно рассмотреть позже, если они понадобятся.

## 11. Нестандартные состояния

Пустые, ошибочные и нестандартные состояния описаны отдельно в `07-empty-and-error-states.feature-spec.md`.

Global spec фиксирует только общий принцип: пользователь не должен попадать в тупик. Если действие невозможно, сайт должен объяснить причину и следующий шаг официальным, понятным текстом.

## 12. Критерии успеха первой версии

Первая версия считается успешной, если:

- клиент может открыть каталог по ссылке и понять доступный ассортимент;
- клиент может собрать заказ и отправить его в WhatsApp;
- работник магазина получает заказ в понятном виде;
- владелец может без разработки поддерживать актуальность каталога;
- сайт заменяет ручную отправку ассортимента и цен клиентам.
