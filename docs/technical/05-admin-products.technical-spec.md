# Technical Spec: Admin Products v0.1

## 1. Назначение

Этот документ описывает техническую работу админки товаров, категорий, вкусов и сортировки.

Он опирается на feature spec `06-admin-products.feature-spec.md`.

## 2. Общая идея

Админка нужна владельцу, чтобы управлять каталогом без разработки.

Все действия в админке выполняются через защищенные серверные API.

Клиенты не имеют доступа к админским страницам и API.

## 3. Админские разделы

В первой версии нужны разделы:

- список товаров;
- добавление товара;
- редактирование товара;
- черновики;
- скрытые товары;
- категории;
- сортировка **Все напитки**;
- сортировка внутри категории.

## 4. Список товаров

Список товаров показывает товары, которые не удалены.

В списке нужно видеть:

- фото;
- название;
- категорию;
- цену;
- количество штук в одной уп;
- статус;
- признак наличия вкусов.

Поиск в админке работает по названию товара.

Скрытые товары и черновики могут быть отдельными списками, но должны быть доступны владельцу.

Удаленные товары в обычном списке не показываются.

## 5. Добавление товара

Технический запрос:

```text
POST /api/admin/products
```

Поля:

- название;
- категория;
- базовая цена;
- количество штук в одной уп;
- основное фото;
- статус;
- признак выбора вкуса;
- вкусы, если они есть.

Новый товар по умолчанию попадает:

- в конец **Все напитки**;
- в конец своей категории.

Если обязательных данных не хватает, товар можно сохранить как черновик.

Если владелец пытается опубликовать товар без обязательных данных, система должна предложить сохранить его как черновик или показать ошибку публикации.

## 6. Редактирование товара

Технический запрос:

```text
PATCH /api/admin/products/{id}
```

Можно менять:

- название;
- категорию;
- цену;
- количество штук в одной уп;
- основное фото;
- статус;
- вкусы;
- фото вкусов;
- цены вкусов.

Если категория товара изменилась:

- товар исчезает из старой категории;
- список старой категории смыкается без пустого места;
- товар попадает в конец новой категории, если владелец не переставил его вручную.

Внутренне порядок можно пересчитать и сохранить последовательными числами.

## 7. Удаление товара

Перед удалением нужно подтверждение.

Технический запрос:

```text
DELETE /api/admin/products/{id}
```

После удаления товар:

- не виден клиенту;
- не виден в обычном списке админки;
- исчезает из корзины клиента при актуализации корзины.

Технически можно использовать `deleted_at`, чтобы не терять запись сразу.

## 8. Статусы товара

Основные статусы:

- `active`;
- `out_of_stock`;
- `hidden`;
- `draft`.

Правила публикации:

- `active` можно поставить только если заполнены обязательные данные;
- `out_of_stock` можно поставить только если заполнены обязательные данные;
- `hidden` не виден клиенту;
- `draft` не виден клиенту.

Обязательные данные для видимости клиенту:

- название;
- категория;
- базовая цена;
- количество штук в одной уп;
- основное фото.

## 9. Вкусы

Если у товара есть выбор вкуса, владелец управляет списком вкусов.

Для вкуса нужны:

- название;
- отдельная цена, если отличается от базовой;
- отдельное фото, если нужно;
- отметка **нет в наличии**;
- порядок.

Если все вкусы отмечены как **нет в наличии**, это не отдельный статус товара. Система вычисляет, что товар виден, но недоступен для заказа.

Если у товара нет выбора вкуса, в клиентском каталоге не нужно заставлять клиента выбирать вкус.

## 10. Категории

Технические запросы:

```text
GET /api/admin/categories
POST /api/admin/categories
PATCH /api/admin/categories/{id}
DELETE /api/admin/categories/{id}
```

Правила:

- название категории обязательно;
- название категории уникально;
- новая категория попадает в конец списка;
- категорию с товарами нельзя удалить;
- порядок категорий меняется через перетаскивание;
- **Все напитки** не создается как категория и не редактируется.

## 11. Сортировка

Сортировка категорий:

```text
POST /api/admin/categories/reorder
```

Сортировка товаров в **Все напитки**:

```text
POST /api/admin/products/reorder-all
```

Сортировка товаров внутри категории:

```text
POST /api/admin/categories/{id}/products/reorder
```

Запрос сортировки передает список `id` в новом порядке.

Сервер сохраняет порядок и нормализует `sort_order`.

Порядок **Все напитки** и порядок внутри категории хранятся отдельно.

## 12. Фото

Загрузка фото описана в `06-images-and-files.technical-spec.md`.

Админка товара должна уметь:

- загрузить основное фото;
- заменить основное фото;
- загрузить фото вкуса;
- заменить фото вкуса;
- оставить вкус без отдельного фото.

Если у вкуса нет отдельного фото, клиентский каталог использует основное фото товара.

## 13. Ошибки и проверки

Нужно обрабатывать:

- пустое название товара;
- отсутствие категории при публикации;
- отсутствие цены при публикации;
- отсутствие количества штук в одной уп при публикации;
- отсутствие основного фото при публикации;
- пустое название вкуса;
- дубль названия категории;
- удаление категории с товарами;
- сохранение некорректной цены;
- сохранение некорректного количества штук в одной уп;
- потерю сессии администратора.

Сообщения должны быть официальными и понятными.

## 14. Вопросы для подтверждения

1. При нехватке обязательных данных система автоматически сохраняет черновик или владелец сам выбирает "Сохранить как черновик"?
2. Нужно ли разрешить товар без выбора вкуса технически иметь один скрытый системный вкус, или проще хранить такие товары без записей во `flavors`?
3. Нужно ли показывать удаленные товары где-то в админке, или они полностью исчезают для владельца?
