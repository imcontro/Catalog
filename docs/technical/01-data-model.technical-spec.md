# Technical Spec: Data Model v0.1

## 1. Назначение

Этот документ описывает черновую модель данных проекта **Каталог NapitkiBerkat**.

Модель данных нужна, чтобы технически поддержать:

- категории;
- товары;
- вкусы;
- цены;
- фото;
- статусы товара;
- ручную сортировку;
- админскую авторизацию.

## 2. Общие принципы

База данных хранит каталог и админские данные.

Корзина клиента в первой версии не хранится в базе данных.

Заказы в первой версии не хранятся в базе данных.

Цены хранятся в рублях целым числом.

Фото хранятся как файлы, а в базе хранится ссылка на файл и технические данные.

Удаленные товары можно хранить через `deleted_at`, чтобы технически отличать удаление от скрытия. Для владельца удаленный товар считается исчезнувшим из админского списка и клиентского каталога.

## 3. Таблица categories

Категория нужна для группировки товаров.

Поля:

- `id` - уникальный идентификатор;
- `name` - название категории;
- `sort_order` - порядок показа категории клиенту;
- `created_at` - дата создания;
- `updated_at` - дата обновления.

Правила:

- название категории обязательно;
- название категории должно быть уникальным;
- новая категория попадает в конец списка;
- категорию с товарами нельзя удалить;
- при переименовании категории товары остаются в этой категории;
- **Все напитки** не хранится как категория в таблице `categories`.

Стартовые категории при первом запуске:

- вода;
- газировки;
- лимонады;
- чай;
- натуральные напитки;
- энергетики;
- разные напитки.

## 4. Таблица products

Товар - основная сущность каталога.

Поля:

- `id` - уникальный идентификатор;
- `name` - название товара;
- `category_id` - ссылка на категорию;
- `price_rub` - базовая цена одной уп;
- `pack_quantity` - количество штук в одной уп;
- `main_image_id` - основное фото товара;
- `status` - основной статус товара;
- `has_flavor_choice` - есть ли у товара выбор вкуса;
- `all_drinks_sort_order` - порядок товара в фильтре **Все напитки**;
- `category_sort_order` - порядок товара внутри своей категории;
- `created_at` - дата создания;
- `updated_at` - дата обновления;
- `deleted_at` - дата удаления, если товар удален.

Статусы товара:

- `active` - доступен для заказа;
- `out_of_stock` - нет в наличии;
- `hidden` - скрыт из клиентского каталога;
- `draft` - черновик.

Правила:

- название обязательно;
- категория обязательна для публикации;
- базовая цена обязательна для клиентского каталога;
- количество штук в одной уп обязательно для клиентского каталога;
- основное фото обязательно для клиентского каталога;
- товар без обязательных данных можно сохранить только как черновик;
- товар со статусом `hidden` не виден клиенту;
- товар со статусом `draft` не виден клиенту;
- товар с `deleted_at` не виден клиенту и не показывается владельцу в обычном списке товаров.

## 5. Таблица product_flavors

Вкус нужен для товаров, у которых есть выбор вкуса.

Поля:

- `id` - уникальный идентификатор;
- `product_id` - ссылка на товар;
- `name` - название вкуса;
- `price_rub` - отдельная цена вкуса, если она отличается от базовой цены товара;
- `image_id` - отдельное фото вкуса, если оно есть;
- `is_out_of_stock` - отметка **нет в наличии** для конкретного вкуса;
- `sort_order` - порядок вкуса внутри товара;
- `created_at` - дата создания;
- `updated_at` - дата обновления.

Правила:

- если у товара включен выбор вкуса, у него должен быть хотя бы один вкус;
- название вкуса обязательно;
- вкус без отдельной цены использует базовую цену товара;
- вкус без отдельного фото использует основное фото товара;
- вкус с `is_out_of_stock = true` виден клиенту, но недоступен для выбора;
- если все вкусы товара недоступны, товар остается видимым, но недоступен для заказа;
- состояние "все вкусы недоступны" не хранится отдельным статусом, а вычисляется.

## 6. Таблица images

Фото хранится отдельной сущностью, чтобы одно фото можно было привязать к товару или вкусу.

Поля:

- `id` - уникальный идентификатор;
- `storage_path` - путь к файлу;
- `public_url` - публичная ссылка на файл;
- `original_name` - исходное имя файла;
- `mime_type` - тип файла;
- `size_bytes` - размер файла;
- `width` - ширина после обработки;
- `height` - высота после обработки;
- `created_at` - дата загрузки.

Правила:

- основное фото товара обязательно для клиентского каталога;
- фото вкуса не обязательно;
- если фото вкуса нет, клиент видит основное фото товара;
- удаление товара не должно ломать фото других товаров или вкусов;
- очистка неиспользуемых фото может быть отдельной технической задачей.

## 7. Таблица admin_sessions

Сессия нужна для входа владельца в админку.

Поля:

- `id` - уникальный идентификатор;
- `session_token_hash` - хеш токена сессии;
- `created_at` - дата создания;
- `expires_at` - дата истечения;
- `revoked_at` - дата выхода, если сессия закрыта.

Правила:

- пароль администратора не хранится в открытом виде;
- для первой версии используется один общий логин и один общий пароль;
- после выхода сессия должна стать недействительной;
- клиентская часть не имеет доступа к сессии администратора.

## 8. Настройки проекта

Часть настроек лучше хранить не в базе, а в переменных окружения:

- логин администратора;
- хеш пароля администратора;
- номер WhatsApp, на который отправляется заказ;
- порог бесплатной доставки;
- публичный адрес сайта.

Порог бесплатной доставки в первой версии: `8000`.

## 9. Вычисляемые значения

### 9.1. Видимость товара клиенту

Товар виден клиенту, если:

- `status` равен `active` или `out_of_stock`;
- `deleted_at` пустой;
- есть категория;
- есть базовая цена;
- есть основное фото;
- есть количество штук в одной уп.

### 9.2. Доступность товара для заказа

Товар доступен для заказа, если:

- товар виден клиенту;
- `status` равен `active`;
- если у товара есть вкусы, хотя бы один вкус доступен.

Товар недоступен для заказа, если:

- `status` равен `out_of_stock`;
- все вкусы товара отмечены как **нет в наличии**;
- выбранный вкус отмечен как **нет в наличии**.

### 9.3. Эффективная цена

Для товара без выбора вкуса:

- цена равна `products.price_rub`.

Для товара с выбранным вкусом:

- если у вкуса есть `price_rub`, используется цена вкуса;
- если у вкуса нет `price_rub`, используется базовая цена товара.

До выбора вкуса карточка товара показывает цену первого вкуса по порядку. Если у первого вкуса нет отдельной цены, показывается базовая цена товара.

### 9.4. Эффективное фото

Для товара без выбранного вкуса:

- показывается основное фото товара.

Для выбранного вкуса:

- если у вкуса есть отдельное фото, показывается фото вкуса;
- если у вкуса нет отдельного фото, показывается основное фото товара.

## 10. Индексы и ограничения

Нужны индексы:

- `categories.sort_order`;
- `products.category_id`;
- `products.status`;
- `products.deleted_at`;
- `products.all_drinks_sort_order`;
- `products.category_sort_order`;
- `product_flavors.product_id`;
- `product_flavors.sort_order`.

Нужны уникальные ограничения:

- уникальное название категории;
- уникальный порядок категории можно поддерживать технически, но при перетаскивании допустима нормализация порядка.

## 11. Вопросы для подтверждения

1. Количество штук в одной уп храним числом и показываем как `{число} шт в уп`, или нужно свободное текстовое поле?
2. Удаление товара делаем мягким через `deleted_at` или физически удаляем запись из базы?
3. Нужно ли хранить историю изменений цен и товаров в будущем, или первая версия может жить без истории?
