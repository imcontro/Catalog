# Technical Spec: Supabase v0.1

## 1. Назначение

Этот документ описывает, как проект **Каталог NapitkiBerkat** использует Supabase.

Supabase нужен в первой версии для двух задач:

- хранить данные каталога в Supabase Postgres;
- хранить фото товаров и вкусов в Supabase Storage.

Этот spec не заменяет `01-data-model.technical-spec.md`. Data model описывает, какие данные есть в проекте. Этот документ описывает, как эти данные и фото размещаются именно в Supabase.

## 2. Что входит в Supabase

В Supabase хранятся:

- категории;
- товары;
- вкусы товаров;
- ссылки на фото;
- сессии администратора, если они хранятся в базе;
- фото товаров и вкусов через Supabase Storage.

В Supabase не хранятся:

- корзина клиента;
- история отправленных заказов;
- личные кабинеты клиентов;
- точные складские остатки;
- история изменения цен и товаров.

## 3. Supabase-проект первой версии

В первой версии используется текущий чистый Supabase-проект как основной рабочий Supabase для каталога.

Отдельный тестовый Supabase-проект не обязателен и не создается только ради деплоя.

В основном рабочем Supabase хранятся:

- реальные категории;
- реальные товары;
- реальные цены;
- реальные фото;
- реальные статусы товаров.

Основной рабочий Supabase можно подключать к Vercel для реальных клиентов, если владелец подтвердил, что данные чистые и готовы к запуску.

Отдельный тестовый Supabase-проект можно создать позже отдельным решением, если понадобятся рискованные эксперименты, массовые проверки импорта или разработка, которую нельзя безопасно выполнять на рабочей базе.

Основной рабочий Supabase нельзя использовать для случайных тестов, массового удаления или рискованных экспериментов без отдельного плана и бэкапа.

## 4. Supabase Postgres

Supabase Postgres хранит основные данные каталога.

Таблицы описаны в `01-data-model.technical-spec.md`:

- `categories`;
- `products`;
- `product_flavors`;
- `images`;
- `admin_sessions`, если сессии администратора хранятся в базе.

Правила:

- структура таблиц создается и меняется через миграции;
- перед изменениями структуры или массовыми изменениями данных нужен понятный план и бэкап;
- если появляется отдельный тестовый Supabase, его структура должна совпадать с рабочим Supabase;
- стартовые категории создаются через миграцию или отдельный стартовый скрипт.

## 5. Supabase Storage

Supabase Storage используется для фото товаров и вкусов.

Нужен bucket:

```text
product-images
```

В этом bucket хранятся:

- основные фото товаров;
- фото вкусов, если они есть.

Bucket `product-images` публичный для чтения фото.

Фото товаров должны быть доступны клиентскому каталогу для просмотра.

Загружать, заменять и привязывать фото может только админка через серверную часть приложения.

Клиентский каталог не должен иметь возможность загружать или менять фото.

## 6. Связь фото с базой

Сам файл фото хранится в Supabase Storage.

В Supabase Postgres хранится запись в таблице `images`:

- путь к файлу;
- публичная ссылка;
- имя файла;
- тип файла;
- размер файла;
- дата загрузки.

Товар хранит ссылку на основное фото через `main_image_id`.

Вкус хранит ссылку на свое фото через `image_id`, если отдельное фото есть.

Если у вкуса нет отдельного фото, клиентский каталог использует основное фото товара.

## 7. Доступы и ключи

Для проекта нужны переменные окружения:

```text
DATABASE_URL
SUPABASE_URL
SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY
SUPABASE_STORAGE_BUCKET
```

`DATABASE_URL` используется сервером для работы с Supabase Postgres.

`SUPABASE_URL` указывает адрес Supabase-проекта.

`SUPABASE_ANON_KEY` можно использовать только для безопасных публичных операций, если они понадобятся.

`SUPABASE_SERVICE_ROLE_KEY` дает полный доступ к Supabase и должен использоваться только на сервере.

`SUPABASE_SERVICE_ROLE_KEY` нельзя отправлять в браузер и нельзя хранить в клиентском коде.

`SUPABASE_STORAGE_BUCKET` для первой версии:

```text
product-images
```

## 8. Правило доступа через сервер

В первой версии клиентский каталог и админка не должны напрямую менять данные в Supabase из браузера.

Правильный путь:

```text
Клиентский интерфейс / админка
↓
API приложения
↓
Supabase
```

Это нужно, чтобы:

- клиент не мог менять товары;
- клиент не мог менять цены;
- клиент не мог загружать фото;
- админские действия проходили через проверку логина и пароля;
- сервер мог применить правила из feature specs.

## 9. Supabase Auth

Supabase Auth в первой версии не используется для входа в админку.

Вход в админку описан в `04-admin-auth.technical-spec.md`.

Для первой версии используется один общий логин и один общий пароль.

## 10. RLS и безопасность таблиц

Так как клиент и админка работают с Supabase через серверный API приложения, прямой доступ из браузера к таблицам не нужен.

Правило первой версии:

- публичный браузер не должен иметь прямого права менять таблицы;
- админские изменения выполняются только сервером после проверки сессии;
- сервисный ключ Supabase хранится только в переменных окружения Vercel;
- секретные ключи не попадают в Git.

Если позже появится прямой клиентский доступ к Supabase, нужно отдельно описать Row Level Security и политики доступа.

## 11. Миграции

Структура базы должна создаваться через миграции.

Для первой версии миграции и схема базы ведутся через Drizzle ORM.

Миграции нужны, чтобы:

- структуру Supabase можно было повторяемо создать заново;
- изменения структуры базы были повторяемыми;
- не создавать таблицы руками каждый раз.

Порядок:

1. Миграция создается в коде проекта.
2. Перед применением к рабочему Supabase проверяется, что миграция соответствует утвержденному work plan.
3. Перед рискованной миграцией или массовым изменением данных делается бэкап.
4. Миграция применяется к рабочему Supabase.
5. После применения проверяется работа каталога, админки и фото.

Если позже будет создан отдельный тестовый Supabase, рискованные миграции сначала проверяются на нем, а потом применяются к рабочему Supabase.

## 12. Стартовые данные

При первом запуске можно создать стартовые категории:

- вода;
- газировки;
- лимонады;
- чай;
- натуральные напитки;
- энергетики;
- разные напитки.

Стартовые категории можно изменить через админку после запуска.

## 13. Бэкапы

Нужно бэкапить:

- Supabase Postgres;
- Supabase Storage bucket `product-images`.

Минимальное правило:

- перед крупными изменениями делать ручной бэкап;
- регулярно сохранять копию базы;
- регулярно сохранять копию фото.

Бэкап базы без бэкапа фото недостаточен, потому что каталог зависит от изображений товаров.

## 14. Vercel и Supabase

Проект размещается на Vercel.

Vercel хранит переменные окружения для подключения к Supabase.

Vercel-деплой первой версии подключается к текущему рабочему Supabase через переменные окружения:

- `DATABASE_URL`;
- `SUPABASE_URL`;
- `SUPABASE_ANON_KEY`;
- `SUPABASE_SERVICE_ROLE_KEY`;
- `SUPABASE_STORAGE_BUCKET`.

Локальная разработка может использовать тот же рабочий Supabase, пока владелец считает его чистым и готовым к запуску. При этом нельзя выполнять случайные тесты, массовые удаления или рискованные изменения без отдельного плана и бэкапа.

Если позже появится отдельный тестовый Supabase, для него должны использоваться отдельные значения `DATABASE_URL`, `SUPABASE_URL`, ключей и при необходимости bucket.

## 15. Что нельзя делать

Нельзя:

- хранить `SUPABASE_SERVICE_ROLE_KEY` в клиентском коде;
- коммитить Supabase-ключи в Git;
- использовать рабочий Supabase для случайных тестов;
- давать клиентскому каталогу право менять товары, цены или фото;
- удалять bucket с фото без бэкапа;
- менять структуру рабочей базы без утвержденного плана и бэкапа.

Связанные документы:

- `04-admin-auth.technical-spec.md` - вход в админку;
- `05-admin-products.technical-spec.md` - управление товарами;
- `06-images-and-files.technical-spec.md` - правила фото;
- `07-deployment-and-operations.technical-spec.md` - деплой, окружения и бэкапы.

## 17. Принятые решения

1. Текущий чистый Supabase-проект используем как основной рабочий Supabase первой версии и не переносим данные в отдельный проект только ради запуска.
2. Отдельный тестовый Supabase-проект не обязателен; его можно создать позже отдельным решением для рискованных экспериментов или крупных проверок.
3. Bucket `product-images` делаем публичным для чтения фото.
4. За бэкапы Supabase после запуска отвечает владелец проекта. Решение также зафиксировано в `07-deployment-and-operations.technical-spec.md`.
