# Work Plan: Supabase и база данных

## Статус

Завершен. Владелец протестировал результат и попросил сделать push на GitHub.

## Ветка

```text
feature/supabase-database
```

## Цель

Подготовить тестовое подключение к Supabase, повторяемую структуру базы данных и базовую серверную проверку чтения данных, чтобы следующие этапы могли работать с реальными таблицами каталога.

## Scope

В рамках этого плана делаем:

- уточнить и зафиксировать техническое решение по ORM, если оно еще не выбрано в technical specs;
- добавить зависимости для работы с Supabase Postgres через выбранный ORM;
- добавить серверную конфигурацию подключения к базе без попадания секретов в клиентский код;
- обновить `.env.example` без реальных значений;
- подготовить миграции для таблиц `categories`, `products`, `product_flavors`, `images` и `admin_sessions`;
- подготовить стартовые категории по data model spec;
- подготовить настройку bucket `product-images` для Supabase Storage или отдельную инструкцию, если bucket создается руками в Supabase;
- добавить минимальный серверный health check или внутренний тестовый read-запрос, который подтверждает доступ к Supabase Postgres;
- проверить, что `SUPABASE_SERVICE_ROLE_KEY` используется только на сервере и не попадает в браузер;
- проверить, что реальные `.env`-значения не попадают в Git.

## Не делаем

- не подключаем боевой Supabase к локальной разработке;
- не загружаем реальные товары и фото старого каталога;
- не пишем импорт старого каталога;
- не реализуем клиентский каталог на реальных товарах;
- не реализуем корзину;
- не реализуем WhatsApp-заказ;
- не реализуем настоящую авторизацию админки;
- не делаем админку управления товарами;
- не настраиваем Vercel и production env.

## Зависимости и данные от владельца

Для полной проверки этапа нужен тестовый Supabase-проект.

Владелец должен предоставить или создать локально значения для тестового окружения:

- `DATABASE_URL`;
- `SUPABASE_URL`;
- `SUPABASE_ANON_KEY`;
- `SUPABASE_SERVICE_ROLE_KEY`;
- `SUPABASE_STORAGE_BUCKET`.

Эти значения нельзя коммитить в Git.

Если тестовый Supabase-проект еще не готов, в рамках этого плана можно подготовить код, миграции и `.env.example`, но нельзя подтвердить реальное применение миграций и чтение из Supabase.

## Открытый технический вопрос

Technical overview уже требует ORM, но конкретный ORM пока не зафиксирован.

Предлагаемое решение для этого плана: выбрать ORM и зафиксировать выбор в technical specs перед добавлением зависимостей и миграций.

## Шаги реализации

1. Перед разработкой перейти на `main`, обновить `main` через `git pull --ff-only origin main` и создать ветку `feature/supabase-database`.
2. Проверить, нет ли незавершенных чужих изменений, которые мешают работе.
3. Уточнить и зафиксировать выбор ORM в technical specs.
4. Добавить зависимости для ORM и подключения к Supabase Postgres.
5. Добавить серверный модуль конфигурации окружения с проверкой обязательных переменных.
6. Подготовить схему базы и миграции по `01-data-model.technical-spec.md`.
7. Добавить стартовые категории через миграцию или отдельный стартовый скрипт.
8. Подготовить правило создания bucket `product-images`.
9. Добавить минимальную серверную проверку чтения из базы.
10. Запустить проверки и убедиться, что секреты не попали в клиентский код или Git.

## Проверка

- `npm run lint`;
- `npm run typecheck`;
- `npm run build`;
- применение миграций к тестовому Supabase, если тестовый проект и env доступны;
- проверка, что таблицы `categories`, `products`, `product_flavors`, `images` и `admin_sessions` созданы;
- проверка, что стартовые категории созданы;
- проверка, что bucket `product-images` существует и публично читает фото;
- проверка серверного read-запроса к Supabase;
- `git diff --check`;
- проверка, что реальные секреты не добавлены в репозиторий.
