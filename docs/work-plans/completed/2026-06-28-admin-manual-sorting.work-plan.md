# Work Plan: Админка - ручная сортировка каталога

Дата: 2026-06-28

Статус: завершен, протестирован владельцем, готов к push

Рабочая ветка после утверждения плана: `feature/admin-manual-sorting`

## 1. Цель

Добавить владельцу ручную сортировку каталога через админку, чтобы без разработки можно было менять:

- порядок реальных категорий;
- порядок товаров в фильтре **Все напитки**;
- порядок товаров внутри отдельной категории.

Главный результат:

```text
Владелец после входа в админку может перетаскивать категории и товары, сохранять порядок, а клиентский каталог показывает этот порядок.
```

## 3. Scope работы

### 3.1. Навигация сортировки в админке

Нужно:

- добавить защищенные разделы сортировки:
  - `/admin/sorting/all` - сортировка товаров в **Все напитки**;
  - `/admin/sorting/category/{id}` - сортировка товаров внутри выбранной категории;
- добавить вход в сортировку из админки и/или разделов товаров и категорий;
- сохранить общий стиль админки, русские тексты, состояния загрузки, ошибок и пустых списков;
- оставить доступ к разделам сортировки только после проверки админской сессии.

Допустимо добавить отдельный блок или вкладки сортировки, если это лучше ложится на текущую структуру админки.

### 3.2. Сортировка категорий

Нужно:

- дать владельцу возможность менять порядок реальных категорий через перетаскивание;
- не показывать **Все напитки** как перетаскиваемую категорию;
- не давать переместить, удалить или переименовать **Все напитки** в рамках сортировки;
- сохранять порядок в `categories.sort_order`;
- после сохранения обновлять список категорий в админке без ручной перезагрузки;
- клиентский каталог должен показывать категории в новом порядке, при этом **Все напитки** остается первым.

Технический API по spec:

```text
POST /api/admin/categories/reorder
```

### 3.3. Сортировка товаров в Все напитки

Нужно:

- дать владельцу возможность менять порядок товаров в **Все напитки** через перетаскивание;
- показывать только неудаленные товары, которые владелец видит в обычных рабочих списках админки;
- сохранять порядок в `products.all_drinks_sort_order`;
- после сохранения обновлять админский список и клиентский каталог;
- не менять категорию товара, статус, цену, фото, вкусы или другие данные товара.

Технический API по spec:

```text
POST /api/admin/products/reorder-all
```

### 3.4. Сортировка товаров внутри категории

Нужно:

- дать владельцу выбор категории для сортировки;
- дать владельцу возможность менять порядок товаров внутри выбранной категории через перетаскивание;
- показывать только товары этой категории, которые не удалены;
- сохранять порядок в `products.category_sort_order`;
- порядок внутри категории должен быть независимым от порядка **Все напитки**;
- после сохранения обновлять админский список и клиентский каталог;
- не переносить товары между категориями в этом интерфейсе.

Технический API по spec:

```text
POST /api/admin/categories/{id}/products/reorder
```

### 3.5. Серверная защита и нормализация порядка

Нужно:

- выполнять сохранение порядка только через защищенные серверные операции после проверки админской сессии;
- не отправлять `SUPABASE_SERVICE_ROLE_KEY` или другие секреты в браузер;
- принимать список `id` в новом порядке;
- проверять, что все переданные `id` существуют и относятся к нужному списку;
- нормализовать порядок последовательными числами без пустых мест;
- корректно обработать:
  - отсутствие админской сессии;
  - пустой список;
  - неизвестный `id`;
  - товар не из выбранной категории;
  - категорию, которая не найдена;
  - сетевую или серверную ошибку Supabase.

## 4. Что не входит в этот план

В этот work plan не входит:

- добавление, редактирование или удаление товаров;
- добавление, переименование или удаление категорий;
- перенос товаров между категориями;
- drag-and-drop вкусов товара;
- изменение фото, цен, статусов, вкусов или количества штук в одной уп;
- сортировка скрытых товаров как отдельного клиентского порядка;
- сортировка черновиков как отдельного клиентского порядка;
- изменение клиентского дизайна каталога, корзины, оформления заказа и WhatsApp-сообщения;
- деплой на Vercel.

## 5. Проверки

После реализации нужно выполнить:

```text
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
git diff --check
git status --short --branch
```

Дополнительно вручную проверить:

- `/admin/sorting/all` без входа переводит на `/admin/login` или не дает выполнить админские действия;
- `/admin/sorting/category/{id}` без входа переводит на `/admin/login` или не дает выполнить админские действия;
- в админке виден вход в сортировку;
- **Все напитки** не показывается как обычная категория для сортировки категорий;
- можно перетащить категории и сохранить порядок;
- после сохранения категорий клиентский каталог показывает новый порядок категорий, а **Все напитки** остается первым;
- можно перетащить товары в **Все напитки** и сохранить порядок;
- после сохранения **Все напитки** клиентский каталог показывает новый порядок товаров в общем фильтре;
- можно выбрать категорию, перетащить товары внутри нее и сохранить порядок;
- после сохранения категории клиентский каталог показывает новый порядок товаров внутри этой категории;
- порядок **Все напитки** и порядок внутри категории могут отличаться;
- при пустой категории показывается понятное пустое состояние;
- при ошибке сохранения владелец видит понятное русское сообщение;
- клиентский каталог не показывает ссылку на админку;
- секреты Supabase не попали в клиентский код.

## 6. Критерии готовности

План считается выполненным, когда:

- владелец может менять порядок категорий через админку;
- владелец может менять порядок товаров в **Все напитки** через админку;
- владелец может менять порядок товаров внутри отдельной категории через админку;
- сервер сохраняет порядок только после проверки админской сессии;
- сервер нормализует `sort_order` без пустых мест;
- клиентский каталог использует сохраненный порядок;
- интерфейс работает на телефоне и desktop;
- проверки завершены успешно;
- результат показан владельцу для ручной проверки.

4. Выполнить только scope этого work plan.
5. Запустить проверки.
6. Показать результат владельцу для ручной проверки.
7. Commit и push делать только после отдельной просьбы владельца.
