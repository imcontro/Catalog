# Work Plan: Админка - управление категориями

Дата: 2026-06-27

Статус: завершен, протестирован владельцем, готов к push

Рабочая ветка после утверждения плана: `feature/admin-categories-management`

## 1. Цель

Добавить владельцу в админке управление списком категорий, чтобы без разработки можно было:

- добавить новую категорию;
- переименовать существующую категорию;
- удалить пустую категорию;
- увидеть понятную ошибку, если категорию нельзя удалить из-за товаров внутри нее.

Главный результат:

```text
Владелец после входа в админку может управлять категориями каталога, а клиентский каталог показывает актуальный список категорий.
```

## 3. Scope работы

### 3.1. Раздел категорий в админке

Нужно:

- добавить или завершить защищенный раздел `/admin/categories`;
- показывать список реальных категорий из таблицы `categories`;
- не показывать **Все напитки** как редактируемую категорию, потому что это системный фильтр, а не запись в `categories`;
- сохранить общий стиль админки, русские тексты, состояния загрузки, ошибок и пустого списка;
- оставить вход в раздел доступным только после проверки админской сессии.

### 3.2. Добавление категории

Нужно:

- дать владельцу форму добавления категории;
- требовать непустое название;
- не разрешать создать дубль названия категории;
- при успешном добавлении ставить новую категорию в конец списка по `sort_order`;
- после добавления обновлять список категорий в админке без ручной перезагрузки страницы;
- использовать русские сообщения об успехе и ошибках.

### 3.3. Переименование категории

Нужно:

- дать владельцу действие для переименования категории;
- требовать непустое новое название;
- не разрешать переименовать категорию в название, которое уже занято другой категорией;
- при переименовании не переносить товары: они остаются привязанными к той же категории по `category_id`;
- после успешного переименования обновлять список категорий в админке;
- клиентский каталог должен видеть новое название категории.

### 3.4. Удаление категории

Нужно:

- дать владельцу действие удаления категории;
- перед удалением показывать подтверждение;
- разрешать удалить только пустую категорию;
- если в категории есть товары, не удалять категорию и показать понятное сообщение: сначала нужно перенести товары в другую категорию или удалить эти товары;
- после успешного удаления обновлять список категорий в админке;
- не ломать товары без категории, которые допустимы только как черновики по существующим правилам.

### 3.5. Серверная защита и API

Нужно:

- выполнять все изменения категорий только через защищенные серверные операции после проверки админской сессии;
- не отправлять `SUPABASE_SERVICE_ROLE_KEY` или другие секреты в браузер;
- корректно обработать:
  - отсутствие админской сессии;
  - пустое название категории;
  - дубль названия категории;
  - категорию, которая не найдена;
  - удаление категории с товарами;
  - сетевую или серверную ошибку Supabase.

Допустимый технический вариант:

```text
GET /api/admin/categories
POST /api/admin/categories
PATCH /api/admin/categories/{id}
DELETE /api/admin/categories/{id}
```

Или близкий вариант, если он лучше ложится на существующую структуру кода.

## 4. Что не входит в этот план

В этот work plan не входит:

- drag-and-drop сортировка категорий;
- drag-and-drop сортировка товаров в **Все напитки**;
- drag-and-drop сортировка товаров внутри категории;
- создание **Все напитки** как записи в базе;
- удаление или переименование фильтра **Все напитки**;
- массовый перенос товаров между категориями;
- изменение формы добавления или редактирования товара, кроме использования актуального списка категорий, если это уже требуется существующим кодом;
- изменение клиентского дизайна каталога, корзины, оформления заказа и WhatsApp-сообщения;
- деплой на Vercel.

## 5. Проверки

После реализации нужно выполнить:

```text
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
git diff --check
git status --short --branch
```

Дополнительно вручную проверить:

- `/admin/categories` без входа переводит на `/admin/login` или не дает выполнить админские действия;
- после входа владелец видит список категорий;
- **Все напитки** не показывается как редактируемая категория;
- можно добавить новую категорию с уникальным названием;
- новую категорию видно в конце списка категорий;
- нельзя добавить категорию с пустым названием;
- нельзя добавить категорию с названием, которое уже существует;
- можно переименовать категорию в уникальное непустое название;
- нельзя переименовать категорию в уже существующее название;
- после переименования товары остаются в этой же категории;
- можно удалить пустую категорию после подтверждения;
- нельзя удалить категорию, в которой есть товары, и сообщение объясняет причину;
- клиентский каталог показывает актуальный список категорий;
- в клиентском каталоге фильтр **Все напитки** остается первым;
- в клиентском каталоге не появилась ссылка на админку;
- секреты Supabase не попали в клиентский код.

## 6. Критерии готовности

План считается выполненным, когда:

- раздел управления категориями доступен владельцу после входа в админку;
- владелец может добавить, переименовать и удалить пустую категорию;
- сервер не дает создать дубль названия категории;
- сервер не дает удалить категорию с товарами;
- **Все напитки** остается системным фильтром и не редактируется как категория;
- клиентский каталог использует актуальные категории;
- интерфейс работает на телефоне и desktop;
- проверки завершены успешно;
- результат показан владельцу для ручной проверки.
