# Work Plan: Подготовка импорта старого каталога

Дата: 2026-06-06

Статус: completed

Рабочая ветка после утверждения плана: `feature/catalog-import-preparation`

## 1. Цель

Подготовить повторяемый и проверяемый импорт данных старого каталога в структуру проекта.

Главный результат этого плана:

```text
Есть скрипты и отчетность, которые показывают, какие категории, товары, вкусы и фото будут загружены в Supabase, без хаоса при повторном запуске.
```

Этот план закрывает этап roadmap **"Подготовка импорта каталога"**.

Финальная загрузка реальных товаров и фото в Supabase выполняется отдельным следующим work plan.

## 4. Scope работ

### 4.1. Проверка и нормализация draft-данных

Нужно:

- проверить структуру `old-catalog-products.draft.json`;
- проверить обязательные поля товара: название, категория, цена, количество штук в одной уп, основное фото;
- проверить вкусы: название, порядок, отдельную цену и отдельное фото, если они есть;
- проверить, что товары без основного фото остаются `draft` и не считаются готовыми к клиентскому каталогу;
- проверить, что `packQuantity` используется как источник количества штук в упаковке;
- не использовать поврежденное текстовое поле `packDisplay` как источник данных;
- проверить дубли естественных ключей товара: категория + название;
- проверить дубли вкусов внутри одного товара.

### 4.2. Маппинг категорий

Старый каталог содержит названия категорий, которые отличаются от стартовых категорий в миграции.

Нужно подготовить явный маппинг:

- `Вода/Минералка` -> `вода`;
- `Газированные` -> `газировки`;
- `Лимонады` -> `лимонады`;
- `Натуральные` -> `натуральные напитки`;
- `Чай` -> `чай`;
- `Энергетики` -> `энергетики`;
- `Напитки разные` -> `разные напитки`.

Если во время работы станет понятно, что пользовательские названия категорий нужно изменить, работу остановить и уточнить у владельца до изменения specs или миграций.

### 4.3. Подготовка импорта фото

Нужно:

- проверить наличие файлов из `mainPhotoFile`;
- проверить, какие файлы из `data/source-old-catalog/photos/` не используются;
- подготовить стабильные пути для Supabase Storage bucket `product-images`;
- подготовить создание записей в таблице `images`;
- для вкусов без отдельного фото использовать основное фото товара по правилам specs;
- не удалять исходные фото старого каталога;
- не удалять неиспользуемые фото без отдельного подтверждения.

В этом плане можно не обрабатывать изображения через отдельную библиотеку. Если ширина и высота не извлекаются без новой зависимости, поля `width` и `height` могут оставаться пустыми.

### 4.4. Скрипты

Добавить скрипты, которые можно запускать повторно:

- валидация draft-данных без записи в Supabase;
- dry-run импорта с отчетом, какие записи будут созданы или обновлены;
- подготовка загрузки фото в Storage;
- импорт с записью только через явный флаг, который не используется в этом work plan.

Ожидаемые npm-команды:

```text
npm.cmd run catalog:import:validate
npm.cmd run catalog:import:dry-run
```

Команду с реальной записью в Supabase можно подготовить, но не запускать как финальную загрузку данных в рамках этого плана.

### 4.5. Отчеты

Нужно обновить или создать отчет по подготовке импорта.

Отчет должен показывать:

- сколько категорий будет связано;
- сколько товаров готово к публикации;
- сколько товаров останется черновиками;
- какие товары не имеют основного фото;
- сколько вкусов будет импортировано;
- сколько фото будет подготовлено к загрузке;
- какие фото не используются;
- есть ли ошибки, которые блокируют импорт.

## 5. Что не входит в этот план

В этот work plan не входит:

- финальная загрузка реальных товаров и фото в Supabase;
- загрузка данных в боевой Supabase;
- очистка таблиц Supabase;
- удаление старых или неиспользуемых фото;
- изменение схемы базы данных;
- изменение утвержденных пользовательских названий категорий без уточнения;
- клиентский каталог на реальных данных;
- корзина;
- оформление заказа и WhatsApp;
- админка управления товарами;
- деплой на Vercel.

## 6. Проверки

После реализации нужно проверить:

```text
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
npm.cmd run catalog:import:validate
npm.cmd run catalog:import:dry-run
git diff --check
git status --short --branch
```

Если dry-run требует переменные окружения Supabase, он должен завершаться понятной ошибкой при их отсутствии и не должен выполнять частичную запись.

## 7. Критерии готовности

План считается выполненным, когда:

- данные старого каталога проверяются автоматической командой;
- dry-run показывает будущий импорт без записи в Supabase;
- товары без основного фото явно остаются черновиками;
- категория каждого товара сопоставлена с существующей категорией проекта;
- фото для товаров и вкусов проверены на наличие;
- отчет по импорту можно прочитать без запуска кода;
- повторный dry-run дает тот же результат;
- реальная запись в Supabase не выполнялась в рамках этого плана.

## 8. Git-порядок после утверждения

После утверждения владельцем:

1. Убедиться, что локальная ветка `main` актуальна.
2. Создать ветку `feature/catalog-import-preparation` от `main`.
3. Выполнить только scope этого плана.
4. Показать результат владельцу для проверки.
5. Commit и push делать только после отдельной просьбы владельца.
