# Work Plan: Клиентский каталог на данных Supabase

Дата: 2026-06-06

Статус: completed

Рабочая ветка после утверждения плана: `feature/client-catalog`

## 1. Цель

Сделать первый видимый клиентский каталог на реальных данных из тестового Supabase.

Главный результат этого плана:

```text
Клиент открывает главную страницу и видит реальные товары, категории, фото, цены, упаковку и вкусы из Supabase.
```

Этот план закрывает этап roadmap **"Клиентский каталог"** без корзины, оформления заказа и WhatsApp.

## 3. Входные данные

Используем:

- текущую структуру базы `categories`, `products`, `product_flavors`, `images`;
- импортированные данные старого каталога в тестовом Supabase;
- публичные ссылки фото из таблицы `images`;
- существующий логотип и текущую базовую страницу `/`.

Ожидаемое состояние тестового Supabase:

- 7 категорий;
- 86 товаров;
- 108 вкусов;
- 82 импортированных фото;
- 4 товара в статусе `draft`, которые не должны попасть в клиентский каталог.

## 4. Scope работ

### 4.1. Серверные данные каталога

Нужно:

- добавить серверный модуль получения клиентского каталога из Supabase Postgres;
- добавить route handler `GET /api/catalog`;
- вернуть категории в порядке `categories.sort_order`;
- вернуть только видимые клиенту товары;
- не отдавать скрытые товары, черновики и удаленные товары;
- не отдавать товары без категории, цены, основного фото или количества штук в одной уп;
- вернуть вкусы товаров в порядке `product_flavors.sort_order`;
- вычислить эффективную цену и фото для первого вкуса;
- вычислить `isOrderable` для товара и вкуса;
- вычислить состояние, когда все вкусы товара недоступны.

### 4.2. DTO клиента

DTO должен содержать только данные, нужные клиентскому каталогу:

- категории: `id`, `name`, `sortOrder`;
- товары: `id`, `categoryId`, `name`, `priceRub`, `packQuantity`, `imageUrl`, `status`, `isOrderable`, `hasFlavorChoice`, `allDrinksSortOrder`, `categorySortOrder`;
- вкусы: `id`, `name`, `priceRub`, `imageUrl`, `isOutOfStock`, `isOrderable`, `sortOrder`.

Точные внутренние поля базы, служебные ключи и секреты не должны уходить в клиентский ответ.

### 4.3. Интерфейс каталога

На странице `/` нужно:

- сохранить видимый логотип NapitkiBerkat;
- показать фильтр **Все напитки** первым;
- показать категории после **Все напитки**;
- по умолчанию показывать товары из **Все напитки**;
- показывать товары в порядке `allDrinksSortOrder` для **Все напитки**;
- показывать товары в порядке `categorySortOrder` внутри выбранной категории;
- добавить поиск по названию товара;
- сделать поиск нечувствительным к регистру;
- искать внутри выбранного фильтра;
- не искать по названиям вкусов;
- показать карточки товаров с фото, названием, ценой и количеством штук в одной уп;
- показать количество штук в формате `{число} шт в уп`;
- показать выбор вкусов для товаров с несколькими вкусами;
- менять фото и цену карточки при выборе вкуса, если у вкуса есть отдельные фото или цена;
- показывать выбранный вкус рядом с названием товара в формате `{название товара} / {название вкуса}`, выделяя часть с вкусом цветом;
- показывать недоступные товары и вкусы визуально слабее;
- показывать официальные пустые состояния для пустого каталога, пустой категории и пустого поиска;
- не показывать видимую ссылку или кнопку перехода в админку.

### 4.4. Границы корзины

Корзина в этот work plan не входит.

Поэтому:

- не добавлять хранение корзины;
- не добавлять счетчик корзины;
- не добавлять изменение количества через плюс и минус;
- не добавлять оформление заказа;
- не формировать WhatsApp-сообщение.

Если на карточке нужен элемент действия, он не должен обещать работающую корзину до отдельного work plan.

### 4.5. Состояние URL

В первой версии каталога можно поддержать параметры:

- `?category={categoryId}`;
- `?search={query}`.

Если это усложнит реализацию, приоритет получает корректная работа фильтра, поиска и карточек на странице. Отдельные страницы категорий не нужны.

## 5. Что не входит в этот план

В этот work plan не входит:

- корзина;
- добавление товара в заказ;
- сохранение корзины между обновлениями;
- доставка;
- оформление заказа;
- WhatsApp;
- вход в админку;
- админка управления товарами;
- загрузка в боевой Supabase;
- исправление отсутствующих фото у 4 черновиков;
- изменение схемы базы данных;
- деплой на Vercel.

## 6. Проверки

После реализации нужно проверить:

```text
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
npm.cmd run db:check
npm.cmd run catalog:import:check
git diff --check
git status --short --branch
```

Дополнительно вручную проверить локально:

- страница `/` открывается;
- `GET /api/catalog` возвращает данные без секретов;
- **Все напитки** выбран первым;
- видно 82 клиентских товара;
- черновики `горная 5л`, `К-13`, `родники 0,5л`, `южания 0.2 детский` не отображаются;
- категории переключают список;
- поиск работает по названию товара;
- поиск не срабатывает по названию вкуса;
- выбор вкуса меняет цену или фото там, где это есть в данных;
- фото товаров загружаются;
- мобильная ширина не ломает карточки и фильтры.

## 7. Критерии готовности

План считается выполненным, когда:

- клиентский каталог использует данные из Supabase;
- клиент видит категории и реальные товары;
- клиент видит фото, цену и количество штук в одной уп;
- **Все напитки** и категории сортируют товары по правилам specs;
- поиск работает внутри выбранного фильтра;
- выбор вкуса работает в карточке товара;
- черновики, скрытые и удаленные товары не показываются;
- пустые состояния понятны и на русском языке;
- проверки завершились успешно;
- результат показан владельцу для ручной проверки.

## 8. Git-порядок после утверждения

После утверждения владельцем:

1. Убедиться, что локальная ветка `main` актуальна.
2. Создать ветку `feature/client-catalog` от `main`.
3. Выполнить только scope этого плана.
4. Запустить проверки.
5. Показать результат владельцу для проверки.
6. Commit и push делать только после отдельной просьбы владельца.
