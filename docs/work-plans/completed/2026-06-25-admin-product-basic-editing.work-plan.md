# Work Plan: Админка - добавление и редактирование базовых данных товара

Дата: 2026-06-25

Статус: завершен, отправлен в GitHub

Рабочая ветка после утверждения плана: `feature/admin-product-basic-editing`

## 1. Цель

Сделать первый рабочий сценарий изменения товаров в админке: владелец может открыть товар из карточного списка, изменить базовые данные, сохранить изменения, а также создать новый товар как черновик.

Главный результат:

```text
Владелец после входа в админку может менять название, категорию, цену, количество штук в одной уп и статус товара без разработки.
```

## 3. Scope работ

### 3.1. Входы в добавление и редактирование

Нужно:

- добавить на `/admin/products` понятную кнопку **Добавить товар**;
- добавить на карточку товара действие **Редактировать**;
- добавить действие **Редактировать** на карточки в `/admin/drafts` и `/admin/hidden`;
- открыть добавление товара по защищенному маршруту `/admin/products/new`;
- открыть редактирование товара по защищенному маршруту `/admin/products/[id]/edit`;
- все новые страницы должны использовать серверную проверку админской сессии.

### 3.2. Форма товара

Нужно:

- сделать общую форму для добавления и редактирования товара;
- в форме должны быть поля:
  - название товара;
  - категория;
  - цена;
  - количество штук в одной уп;
  - статус товара;
- показывать текущее основное фото товара при редактировании, если оно есть;
- если фото нет, показывать состояние **Фото не добавлено**;
- для нового товара по умолчанию использовать статус `draft`;
- для нового товара не создавать записи вкусов;
- для нового товара `has_flavor_choice` по умолчанию остается `false`.

### 3.3. Сохранение нового товара

Нужно:

- добавить защищенный серверный API:

```text
POST /api/admin/products
```

- создать товар в таблице `products`;
- новый товар по умолчанию ставить:
  - в конец **Все напитки** через `all_drinks_sort_order`;
  - в конец выбранной категории через `category_sort_order`, если категория выбрана;
- разрешить сохранить новый товар как черновик без категории, цены, количества штук в одной уп и фото;
- не публиковать новый товар со статусом `active` или `out_of_stock`, если не заполнены обязательные данные для клиентского каталога.

### 3.4. Сохранение изменений товара

Нужно:

- добавить защищенный серверный API:

```text
PATCH /api/admin/products/{id}
```

- разрешить менять:
  - название;
  - категорию;
  - цену;
  - количество штук в одной уп;
  - статус товара;
- если категория товара изменилась:
  - товар исчезает из старой категории;
  - список старой категории смыкается без пустого места;
  - товар попадает в конец новой категории;
- не менять основное фото товара в этом plan;
- не менять вкусы товара в этом plan;
- не менять признак `has_flavor_choice` в этом plan.

### 3.5. Правила статусов и обязательных данных

Нужно:

- разрешить статус `draft` для незаполненного товара;
- разрешить статус `hidden` для товара, который не должен быть виден клиенту;
- разрешить статус `active` только если заполнены:
  - название;
  - категория;
  - цена;
  - количество штук в одной уп;
  - основное фото;
- разрешить статус `out_of_stock` только при тех же обязательных данных, что и `active`;
- если владелец пытается поставить `active` или `out_of_stock` без обязательных данных, показать понятную ошибку;
- система не должна автоматически превращать товар в черновик без решения владельца.

### 3.6. Возврат после сохранения

Нужно:

- после успешного создания товара открыть страницу редактирования созданного товара или вернуться к списку так, чтобы владелец понял, что товар сохранен;
- после успешного редактирования вернуться к списку товаров, черновиков или скрытых в зависимости от итогового статуса товара;
- показывать понятную ошибку, если сохранение не удалось;
- если товар не найден или удален, показать понятное состояние или вернуть владельца к списку.

### 3.7. Интерфейс и адаптив

Нужно:

- форма должна быть удобна на телефоне и desktop;
- пользовательские тексты, кнопки, ошибки и состояния должны быть на русском языке;
- не добавлять ссылку на админку в клиентский каталог;
- не отправлять секреты в браузер.

## 4. Что не входит в этот план

В этот work plan не входит:

- загрузка нового фото;
- замена основного фото;
- загрузка или замена фото вкуса;
- управление вкусами товара;
- изменение `has_flavor_choice`;
- отдельные цены вкусов;
- отметка отдельного вкуса как **нет в наличии**;
- удаление товара;
- скрытие товара отдельной быстрой кнопкой с карточки;
- возврат скрытого товара отдельной быстрой кнопкой с карточки;
- управление категориями;
- сортировка категорий;
- drag-and-drop сортировка товаров;
- создание новых таблиц или миграций;
- изменение клиентского каталога, корзины, оформления заказа и WhatsApp-сообщения;
- деплой на Vercel.

## 5. Проверки

После реализации нужно выполнить:

```text
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
git diff --check
git status --short --branch
```

Дополнительно вручную проверить:

- `/admin/products/new` без входа переводит на `/admin/login`;
- `/admin/products/[id]/edit` без входа переводит на `/admin/login`;
- после входа кнопка **Добавить товар** открывает форму нового товара;
- новый товар можно сохранить как черновик;
- новый черновик появляется в `/admin/drafts`;
- товар с пустым названием нельзя сохранить;
- товар нельзя опубликовать как `active` или `out_of_stock` без обязательных данных;
- существующий товар можно открыть на редактирование из `/admin/products`;
- существующий товар можно открыть на редактирование из `/admin/drafts`;
- существующий товар можно открыть на редактирование из `/admin/hidden`;
- можно изменить название товара;
- можно изменить категорию товара;
- можно изменить цену товара;
- можно изменить количество штук в одной уп;
- можно изменить статус товара;
- после смены статуса товар попадает в правильный список;
- после смены категории товар отображается в новой категории;
- кнопка выхода из админки продолжает работать;
- в клиентском каталоге не появилась ссылка на админку.

## 6. Критерии готовности

План считается выполненным, когда:

- владелец может создать новый товар как черновик;
- владелец может открыть существующий товар и изменить базовые данные;
- сервер не публикует товар без обязательных данных;
- изменение статуса корректно переносит товар между обычным списком, черновиками и скрытыми;
- изменение категории сохраняется и не ломает порядок товаров;
- все новые админские страницы и API закрыты проверкой админской сессии;
- интерфейс работает на телефоне и desktop;
- проверки завершены успешно;
- результат показан владельцу для ручной проверки.

После утверждения владельцем:

3. Выполнить только scope этого work plan.
4. Запустить проверки.
5. Показать результат владельцу для ручной проверки.
6. Commit и push делать только после отдельной просьбы владельца.
