# Work Plan: Проверка нестандартных состояний перед деплоем

## 1. Статус

Подготовлен для утверждения владельцем.

## 2. Ветка

Планируемая ветка:

```text
feature/nonstandard-states-predeploy-check
```

## 3. Цель

Проверить клиентский каталог, корзину, оформление заказа и админку в нестандартных состояниях перед подготовкой деплоя на Vercel.

Главная цель: пользователь не должен попадать в тупик. Если действие невозможно, интерфейс должен коротко и понятно объяснять причину и следующий шаг.

## 4. Источники требований

- `docs/00-global-spec.md`
- `docs/features/01-client-catalog.feature-spec.md`

## 5. Что делаем

### 5.1. Клиентский каталог

Проверить и при необходимости точечно исправить:

- пустой каталог;
- пустую категорию;
- поиск без результата;
- отображение товара **нет в наличии**;
- товар с выбором вкуса, где часть вкусов недоступна;
- товар с выбором вкуса, где все вкусы недоступны;
- отсутствие черновиков, скрытых и удаленных товаров в клиентском каталоге.

### 5.2. Корзина

Проверить и при необходимости точечно исправить:

- пустую корзину;
- корзину, где остались только недоступные позиции;
- позицию, которая стала **нет в наличии** после добавления;
- позицию, цена которой изменилась после добавления;
- исчезновение скрытого или удаленного товара после актуализации корзины;
- подсказку бесплатной доставки при сумме меньше и больше `8000` руб.;
- запрет оформления заказа, если нет доступных позиций.

### 5.3. Оформление заказа и WhatsApp

Проверить и при необходимости точечно исправить:

- обязательность адреса доставки;
- обязательность способа оплаты;
- официальный текст ошибки, если WhatsApp не открылся;
- состав WhatsApp-сообщения: только доступные позиции, актуальные цены, адрес, оплата и строка доставки.

### 5.4. Админка

Проверить и при необходимости точечно исправить:

- неверный логин или пароль;
- пустой логин и пустой пароль;
- защиту `/admin` без сессии;
- публикацию товара без обязательных данных;
- сохранение незаполненного товара как черновика;
- удаление категории с товарами;
- загрузку неподходящего фото: неверный формат, слишком большой файл, файл не изображения;
- сохранение старого фото при неудачной загрузке.

### 5.5. Проверка перед реальным запуском

Пройти основной smoke-check:

- каталог открывается с телефона и компьютера;
- товары, категории, фото и цены отображаются;
- поиск работает по названию товара;
- корзина считает сумму;
- адрес и способ оплаты обязательны;
- WhatsApp-сообщение формируется правильно;
- админка открывается только после входа;
- товар можно добавить, изменить, скрыть и вернуть;
- фото можно загрузить через админку.

## 6. Что не делаем

- Не настраиваем Vercel.
- Не подключаем домен.
- Не создаем новый Supabase-проект.
- Не меняем схему базы данных без отдельного утверждения.
- Не меняем бизнес-логику каталога, корзины, оформления заказа, WhatsApp и админки.
- Не добавляем новые функции управления каталогом.
- Не добавляем онлайн-оплату, регистрацию, личные кабинеты, CRM, точные складские остатки или сложные роли.
- Не добавляем копирование WhatsApp-сообщения и предпросмотр WhatsApp-сообщения, потому что specs первой версии этого не требуют.

## 7. Технический подход

- Сначала пройти существующие сценарии и найти расхождения с specs.
- Если состояние уже работает по specs, код не менять.
- Если найдено расхождение, исправлять минимально в соответствующем компоненте, API или стиле.
- Пользовательские сообщения держать короткими, русскими, официальными и нетехническими.
- Не трогать серверную бизнес-логику без необходимости.
- Не подключать новые зависимости.

Ожидаемые зоны возможных правок:

- `src/app/page.tsx`
- `src/app/cart/**`
- `src/components/**`
- `src/app/admin/**`
- `src/components/admin/**`
- `src/app/api/**`
- `src/app/globals.css`

## 8. Проверки

Обязательные проверки перед передачей владельцу:

- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd run build`
- `git diff --check`

Ручная проверка:

- `/` открывается и показывает корректные пустые/поисковые состояния;
- `/cart` корректно показывает пустую корзину и недоступные позиции;
- оформление заказа не отправляется без адреса или способа оплаты;
- WhatsApp-сообщение содержит только доступные позиции;
- `/admin/login` показывает общую ошибку входа;
- `/admin` без сессии переводит на `/admin/login`;
- форма товара объясняет обязательные данные перед публикацией;
- удаление категории с товарами запрещено понятным сообщением;
- загрузка неподходящего фото дает понятную ошибку;
- телефонная и desktop-версии остаются читаемыми после исправлений.

## 9. Критерии готовности

План считается выполненным, если:

- все нестандартные сценарии из раздела 5 проверены;
- найденные расхождения со specs исправлены точечно;
- пользовательские сообщения не оставляют клиента или владельца в тупике;
- бизнес-логика первой версии не расширена сверх specs;
- проверки из раздела 8 выполнены;
- владелец вручную проверил результат перед push.

## 10. Порядок работы после утверждения

1. Убедиться, что локальная ветка `main` актуальна.
2. Создать ветку `feature/nonstandard-states-predeploy-check` от `main`.
3. Пройти сценарии из раздела 5.
4. Зафиксировать найденные расхождения.
5. Исправить только подтвержденные расхождения со specs.
6. Выполнить проверки из раздела 8.
7. Передать владельцу для ручной проверки.
8. После просьбы владельца сделать push:
   - перенести work plan из `active/` в `completed/`;
   - обновить `docs/roadmap/timeline.md`;
   - обновить нужные файлы в `docs/roadmap/areas/`;
   - сделать commit и push ветки.
